= Eager execution: backends and kernels
:description: A map of SKaiNET's eager compute path — the TensorOps backend, its pluggable kernel providers, what runs on which platform, and the gaps.

The eager path is `DirectCpuExecutionContext → DefaultCpuOps* → KernelRegistry → KernelProvider`,
distinct from the StableHLO/IREE export path. This page is the hand-authored overview; its
companion xref:reference/kernel-support-matrix.adoc[kernel × platform matrix] is generated from
the registered providers and gated against drift.

This page covers the provider tier — who can compute what, on which platform. The generic path
selects differently, on a declared descriptor of the operands rather than on dtype and priority:
see xref:explanation/kernel-selection.adoc[Kernel SPI and the selection algorithm] for
`KernelDispatch`, the `ViewKernelPack` SPI, and how a call site is matched to a kernel.

Resolution is by priority: *Native (100 — whichever of FFM/JNI/cinterop applies to the target) →
Panama / Wasm SIMD128 (50) → Scalar (0)*. The best *available* provider that carries the kernel wins;
otherwise it cascades down. At most one native tier is compiled into a given target, so the native
columns are mutually exclusive per platform rather than stacked. The Wasm SIMD128 column is the
sidecar pack (`skainet-backend-wasm-simd`), present only after `WasmSimd.install()`; every matmul
kernel in it has an explicit SIMD128 body (the K-quant int8 dots on `i32x4.dot_i16x8_s`, a 4×8
register-blocked dense GEMM, eight-wide BF16/FP16 widening), and the dense kernels thread over the
sidecar's pthread pool like the packed ones when the page is cross-origin isolated. The ternary
kernels in the sidecar are the portable mirror of the vendored NeoGPU kernel — the same 256-entry
decode table as a compile-time constant, read four codes at a time in SIMD128 — registered under the
same dispatch keys as the FFM and JNI ternary packs (`WasmTernaryKernelPack`).

The dense `x · Wᵀ` row is the product a `Linear` layer computes. The JVM and the wasm tier multiply
the `[out, in]` weight in place through `skainet_fp32_matmul_wt` (`KernelProvider.matmulFp32Wt`;
the JVM makes a heap weight resident off-heap once, the sidecar keeps it in its linear memory) and
never materialise the transposed copy the Panama path caches per weight.

Packed weights reach a kernel through the registry by declaring their
xref:explanation/packed-weight-layout.adoc[block order]; a canonical weight is relayouted once,
not per call.

== Platform × what runs

[cols="1,1,2",options="header"]
|===
| Target | Providers available | Notes
| *JVM* | Scalar + Panama + Native-FFM | Full SIMD/native acceleration.
| *Android* | Scalar + Native-JNI | Panama (`jdk.incubator.vector`) and FFM (`java.lang.foreign`) are JDK-only — ART has neither, so Android's native tier is JNI, not a degraded JVM. Includes the NEON `bitnet_gemv` pack.
| *Kotlin/Native — linux x64/arm64* | Scalar + Native-cinterop | Static archive embedded in the klib; manual `installNativeKernels()`, no ServiceLoader on K/N.
| *Kotlin/Native — macOS/iOS* | Scalar + Apple Accelerate + Native-cinterop | Accelerate covers dense FP32 and reductions; cinterop covers packed quant with runtime `FEAT_DotProd` dispatch, so one archive serves A12 through M-series.
| *JS / WASM (Js, Wasi)* | Scalar; wasmJs + `skainet-backend-wasm-simd` | No SIMD in Kotlin code: packed weights are relaid once per weight into kernel feed order and served by the scalar packed kernels; dense `[out, in]` weights are multiplied in place without a transpose copy (SKEEP-007 Tier 0). On wasmJs, `WasmSimd.install()` adds the SIMD128 sidecar pack — the engine's C kernels compiled by Emscripten, with pthreads on cross-origin-isolated pages (SKEEP-007 Tier 1) — and binds `HOST_OFFHEAP` to the sidecar's linear memory, so matmul outputs, elementwise arithmetic, activations and reductions stay resident there between kernels and cross back to the Kotlin heap only when read.
|===

Packed-quant matmul works on every target: those formats have a `commonMain` scalar kernel and
`DefaultCpuOpsBase` dispatches packed weights through the registry.

== Gaps

* *Wasm beyond matmul, part two* — softmax, the normalisations and attention are still the common
scalar Kotlin paths on wasmJs. Elementwise arithmetic, the activations and `sum`/`mean` already run
in the sidecar with the activations kept resident in its linear memory (`Storage.WasmLinear`,
`WasmCpuOps`); the remaining ops follow as fused kernels on both tiers (SKEEP-007 rollout step 3).
* *Native JNI dense FP32/BF16* — the Android JNI provider has no GEMM shim, so dense ops fall
through to scalar there whichever `.so` tier loaded (SKaiNET#920).
* *Dense FP32/BF16 SIMD on Kotlin/Native linux* — still the scalar floor; Apple has Accelerate
(SKaiNET#722, #910).
* *Other GGML quant formats* (Q2_K, Q3_K, Q8_K, IQ4_NL/XS) — loadable via dequantization to FP32,
no packed matmul kernel on any provider.
* *Non-CPU eager backends* (IREE, Metal, GPU) — the `KernelProvider` SPI anticipates them, none
are implemented for the eager path. The *compiled* path (DSL → StableHLO → IREE) does reach GPU on
Android via Vulkan, but that is a separate pipeline.
